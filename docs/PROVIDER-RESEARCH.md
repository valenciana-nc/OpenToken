# Provider authentication and usage audit

## Why this audit exists

A simple button is not an integration. Completion requires (1) usable authentication, (2) a justified account/credential scope, (3) a real usage source, (4) safe persistence and refresh, and (5) visible UI/tray state after restart. Earlier work shipped eight catalogue-only tiles and relied on synthetic noninteractive login children; it did not establish that interactive Windows login could work. This record distinguishes research, code, fixture acceptance and live-provider acceptance.

Research on 2026-10-17 used public official documentation plus a pinned CodexBar snapshot, **steipete/CodexBar `6480977b47f6e4ffd5dcaae1cb0c7fdf34ee449e`**. Downloaded source was read, not executed or bundled. Original Rust implementations were written for OpenToken. Local snapshots and SHA-256 manifests live under `%LOCALAPPDATA%/OpenToken-build/provider-research/`: `manifest.json` (288 source/doc snapshots), `plugins-manifest.json`, `go-manifest.json`, `official/manifest.json`. Saving a snapshot is not a claim every downloaded file was reviewed; the specific protocol/implementation files below were inspected. CodexBar remains MIT; protocol findings and the existing artwork pin are separate.

Follow-up discovery-first behavior is documented in [SOURCE-ARCHITECTURE.md](SOURCE-ARCHITECTURE.md); official login is recovery/add-account setup, not the default monitoring mechanism. New focused research for the last three providers is in [REMAINING-PROVIDERS.md](REMAINING-PROVIDERS.md). In particular, Devin now has an evidenced official Windows CLI credential path, and Muse an official last-observation protocol; neither was implemented merely by researching it.

## Grok continuation: original read-only native session adapter

`grok_personal.rs` implements the researched path, not an xAI management-key/inference endpoint or copied client registration. The official `grok login` owns authentication and credentials. Cached UI status reads do no credential I/O. A fresh installed-session token is read from the selected absolute `GROK_HOME`/standard `.grok/auth.json` only after explicit sign-in or persisted monitoring, with bounded zeroizing reads, regular/unlinked path checks, expiry/ambiguity/team rejection and ignored refresh-token fields. Userinfo checks authenticated subject/email before and after billing; a final exact local-token comparison rejects rotations/account switches. No secret goes to the frontend or OpenToken vault. Disconnect removes monitoring only.

The billing parser keeps credit-usage percentage, separate explicitly reported on-demand budget and prepaid USD balance distinct. Missing usage never becomes 0%, on-demand spending is not relabelled subscription allowance, no reset is invented and invalid optional cent values cannot manufacture a wallet balance. `grok_cli` provenance appears in card details, panel, grid tooltip, tray tooltip and read-only API. This private endpoint can change; real entitlement/CLI OAuth completion still need the user's acceptance. Five additional backend tests include actual HTTP connect/read/disconnect with an unavailable vault, identity/token changes, denied/unknown responses, expiry/team/ambiguous profiles, read-only files and no fabricated quota. Three browser cases cover one-action connection/persistence/disconnect, cancellation/late completion across navigation and missing-CLI handling. Native smoke checks the cached/explicit-start boundary without reading a real Grok profile.

## Reproduced Windows login bug

`cli_sign_in.rs` previously launched a native GUI child's CLI through `std::process::Command` with CREATE_NEW_CONSOLE but inherited standard handles. Under the real GUI/test parent these can be redirected pipes or absent, which does not satisfy an interactive CLI's terminal contract. The old portable was run with a synthetic login executable: **stdin=false, stdout=false, stderr=false** for `IsTerminal`. Previous synthetic children never exercised that requirement.

`login_process.rs` now uses Windows CreateProcessW with a new console, no handle inheritance and no STARTF_USESTDHANDLES. The OS supplies actual console handles. No command shell, user-supplied executable/arguments or elevation is used. The owned process handle is polled, terminated only for its own cancelled/timed-out run, and closed through RAII. API/model-token/alternate-endpoint and nested-Claude/simple-mode overrides are stripped. Code reads no password/CLI output. Both the dedicated `scripts/login-console-probe.mjs --assert` and the full native smoke assert all three streams are real terminals. This proves the launcher contract, not that a user completed a provider's browser login.

CLI waiting is now 10 minutes so ordinary MFA/SSO is not killed after two minutes. The user can cancel waiting; verification already handed to the engine may finish. Cursor's existing desktop wait remains two minutes.

## Copilot correction and ownership

The prior billing-only recommendation was too narrow for displaying actual Copilot allowance. CodexBar's primary quota path was reviewed, but its device flow contains **VS Code's client ID**, which OpenToken does **not** adopt. Instead an installed official `gh` owns browser/device login, requested permissions, credentials and its active account. GitHub CLI can request its usual broader permissions; the official consent screen controls that grant, and the OpenToken button/progress disclose the delegation. OpenToken calls only identity and quota endpoints. No claim is made that this is an OpenToken OAuth application or a least-privilege read:user-only GitHub grant.

Native cached status does not read credentials. An explicit start (or an already persisted GitHub-CLI connection on refresh) runs bounded `gh auth token --hostname github.com` against the selected CLI config directory, with ambient token overrides removed. Secret output stays in zeroizing Rust buffers, is never logged/exported to IPC, and is not copied to Windows Credential Manager by OpenToken. Numeric authenticated identity before/after usage and a final exact local-token reread reject account switches. Disconnect removes monitoring metadata only, never `gh auth logout` or token revocation. Changing the active GitHub account requires explicit reconnecting; one standard CLI profile is monitored at a time. This private endpoint may reject a particular OAuth client or seat; that is a real access error, not success.

Only supplied metered percentages/reset dates become bars; unlimited and zero-entitlement placeholder buckets are omitted. AI credits remain a reported numeric lane without an invented entitlement denominator. Organization entitlement snapshots are not mixed with personal billing records or invoices.

## New API-key adapters

All four are original Rust adapters using fixed HTTPS destinations, redirect-disabled bounded JSON, sanitized errors, provider backoff, 15-second connect spacing, 20/hour verification gates, Windows Credential Manager and the existing atomic/rollback persistence transaction. Region switches clear unsaved keys; region and a non-reversible credential fingerprint scope identity/cache entries. These endpoints do not necessarily expose a person identifier: cards explicitly say **API key**, never an invented email or authenticated human identity. Rotating a key is a new credential scope.

Backend fixtures make actual HTTP requests and exercise connect, parsing, secure storage, refresh, restart metadata, no-secret serialization and disconnect for every new API provider. Unknown schemas, missing counts, invalid regions, nonfinite/negative data and absent limits fail closed. Balance-only data never becomes percentage-left; recorded CLI history/spending estimates remain separate. UI demos are sample-only, not evidence of production authentication.

## Acceptance boundary

Code/fixture acceptance is not live-provider acceptance. This research did not scrape user browser cookies, read real Cursor/Grok/Muse credentials, ask for passwords/tokens in chat, mint a vendor key, register a foreign OAuth app, issue model requests or install/run remote scripts. Only explicitly user-started provider login in the production app should complete a new real authorization. Existing live Codex readings remain working while isolated tests run. Final test/build/deployment results are recorded in [VERIFICATION.md](VERIFICATION.md).
