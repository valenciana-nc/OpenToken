# Provider connections

**Current default: discovery → use existing access → verified reads; sign-in is explicit recovery, not tracking.** The grid is a capability catalogue, not proof of twelve working quota readers. Local tokens and subscription monitoring are independent. See [the source architecture](SOURCE-ARCHITECTURE.md) for implemented coverage, native ownership, test evidence and unfinished readers.

## Saved monitoring versus current usage availability

A saved connection is not deleted because a read fails. **Monitoring saved · cached usage** means the last successful observation remains available but is **not live**; **usage unavailable** means no trustworthy current/cached reading exists. Temporary failures retry automatically without inviting another login. Authentication/identity/permission failures still drop untrusted quota and expose explicit account setup. The grid's current-usage stripe is withheld when stale; the native tray registration stays present with cached/error styling. No percentage is invented to make the connection look healthy.

Grok/Copilot's read-only identity/quota GETs have at most one 250ms-delayed retry per transient transport/408/500/502/503/504 failure, within the existing 45-second operation and scheduled read budget. No retries for rejected credentials, permission denial, malformed data, redirects or provider pauses; Retry-After on server errors is honored as backoff. Error-stage logs contain only provider, fixed stage and fault kind, never credentials/raw responses. GitHub CLI's bounded credential read distinguishes known no-login errors from a transient OS credential-store failure, rather than labelling every failed child as signed out. It never renews credentials.

Persisted Grok profiles receive read-only auth-file change detection plus minute reconciliation. Token/subject changes invalidate previous quota without purchasing an extra network request or bypassing pauses. Partial writes and expiry hints alone do not prove a different login. A truly rejected saved bearer still needs separately approved official-client recovery; these resilience changes do not restore entitlement or silently launch `grok models`/OAuth.

## Connect Antigravity, Devin and Muse

- **Antigravity → Monitor with agy CLI**: native default-No approval enables repeated version-gated, noninteractive `agy --print /usage --output-format json` reads. The CLI may renew its own saved login; no model prompt, borrowed registration, token copy or installer is used. This is a **current CLI profile**, not a verified human account, and is never assigned to the selected person or local history. Cards, API and tray retain `antigravity_cli_usage` provenance; old reports are dropped after failed reads/restart and expired windows never become full. Disconnect stops monitoring and leaves provider sign-in intact. Recovery backups omit this background-owner-operation grant. See [the comparison of other implementations](ANTIGRAVITY-RESEARCH-2026-10-19.md).
- **Antigravity → Use existing Antigravity**: the running signed-in standalone app and IDE are checked independently; an old Roaming folder cannot shadow the IDE. Multiple active profiles fail rather than select an account by folder order. When neither service is running, the exact IDE stored OAuth topic is checked before the separate agy entry. `antigravity_stored` validates fixed deployment and active non-GCP tier before daily-only quota; it never calls onboarding or substitutes production quota. An existing agy installation can separately reuse a structurally valid saved bearer from exactly `gemini:antigravity` in Windows Credential Manager, read-only after this explicit action. Cached expiry alone is not authentication. No vault enumeration or provider token copy/write/renewal occurs. Google identity surrounds the daily-host quota read and the entry is reread afterward. The daily endpoint is canonical for this source; production Gemini is a different pool and is never merged. Provider-rejected access requires official owner recovery. The separate [Session recovery actions](SESSION-RECOVERY-2026-10-19.md) open the selected installed IDE/app or run `agy models`; no prompt or OpenToken grant renewal is used. Desktop reads retain all ownership safeguards: Rust verifies the executable location, same-user SID/session, process lifetime, CSRF and PID-owned IPv4 listener before using fixed loopback RPC paths, then verifies the signed-in email and ownership again. Unknown/custom installs, ambiguous multiple servers using the same profile, missing identity and missing quotas fail honestly. Self-signed TLS handling is isolated to this no-proxy/no-redirect loopback client. No Google OAuth token/client registration is borrowed or refreshed; no app is launched or installed by discovery or existing-source reads. Explicit recovery can open only the selected installed client.
- **Devin → Use existing Devin**: uses the official CLI's current Windows credential file, or when absent the standard Devin desktop `%APPDATA%/Devin/User/globalStorage/state.vscdb` exact `windsurfAuthStatus` record. SQLite access is bounded/read-only, respects WAL and does not copy/checkpoint the database or create sidecars. Desktop deployment overrides and the login-selected server in `codeium.windsurf` are checked before/after; custom tenants are not forwarded to cloud. Both modes use the fixed HTTPS quota host and exact post-read credential/context comparison. OpenToken identifies itself honestly; `ideName=devin` selects the monitored product, `ideVersion=unknown` avoids a fabricated installed version, and extension/User-Agent identify OpenToken. Only supplied unambiguous percent-remaining fields become used-percent models/remaining bars. A hidden daily field is not relabelled weekly; missing/reset-only fields stay unknown. Custom deployment URLs are refused, not silently redirected/fallen back. The card explicitly identifies CLI or app credential scope, not a guessed authenticated person. Cursor 3.24.18 and Devin desktop 3.10.67 now have real existing-session acceptance on this machine; see [the compatibility investigation](COMPATIBILITY-2026-10-19.md).
- **Muse Code → Use existing Muse Code**: asks the installed official CLI only for MSP initialization and `usage/read` (or accepts its `usage/changed` notification). It creates no agent session, sends no prompt and requests no key mint. A safely readable inline `dca:` OAuth profile is required to bind scope; keyring-only/unsupported profiles fail rather than assigning an anonymous meter. A new host can have no last-observed reading; that is unavailable, not 100% left. Observation time is preserved; expired windows are removed without extrapolating resets. **Track local usage** remains independent and works without quota access.
- **Muse advanced subscription refresh**: expand the advanced option, read the warning, choose **Review key endpoint & connect**, then explicitly approve the separate **default-No native Windows confirmation**. Meta's `/muse-code/key` response can contain real quota but may also issue/rotate a CLI inference key; replacement effects are undocumented and could affect running sessions. Requests repeat under the ordinary background budget until this mode is disconnected. OpenToken discards returned inference keys, never uses them for inference or writes Muse's credentials, sends no model prompt and performs no payment operation. A request already sent cannot be undone, including after cancellation or a failed settings save. Missing/idle quota or missing authenticated identity is an error, not a fake connected account. This mode is never an automatic fallback from MSP. Automatic settings-backup recovery deliberately omits this credential-issuing grant; reauthorize it if recovery drops the connection. Removed connection permissions are also excluded from new recovery backups so disconnect is not silently undone.

**Cancel source check** stops an owned probe and prevents an uncommitted connection; it does not revoke provider access. Cached source inventory does not read secrets or launch a process. New scope/file changes clear stale quota without bypassing provider read spacing. Disconnect removes monitoring metadata only and leaves provider sessions/processes/files intact. Antigravity/Devin local token history is not implemented; Muse/Grok/Kimi history remains separate. Live private-API entitlement and every vendor/profile version still require user/provider acceptance. Protocol details and pinned evidence: [REMAINING-PROVIDERS.md](REMAINING-PROVIDERS.md).

## Connect Grok

Select **Grok → Use existing Grok**. An eligible official CLI session is verified without launching login. For recorded this-device turns, **Track local usage** is independent. Missing access does not start authentication; **Account setup (only if needed)** offers the separate official CLI recovery. Nothing is installed automatically. The installed CLI keeps its credentials and owns renewal; OpenToken never refreshes them or copies them into its vault. Identity is checked through xAI's authenticated userinfo before/after the private CLI billing read, followed by an exact local-token comparison. Team/ambiguous/linked profiles fail safely; separate cached expiry is not an authoritative rejection. **Recover Grok session** explicitly runs `grok models`; **Sign in with Grok** now runs `grok login --device-auth`. Enter the terminal's device code on the official page the CLI opens, then leave the terminal open until completion. **Browser return-code help → Use browser sign-in instead** retains `grok login --oauth`: if the loopback return fails, paste the **full return URL**, not just the code, into the original terminal at `Paste the URL here if it doesn't connect`. The terminal is titled **OpenToken - Grok sign-in**; Alt+Tab returns to it. No return code/URL is collected in OpenToken or chat. The CLI may restore its own session, but model-list exit alone is not quota readiness and OpenToken never silently falls through to the new OAuth command. Only supplied credit percentages, explicitly separate on-demand budgets and prepaid balances are shown. Missing usage is unknown, not zero. Disconnect removes monitoring, not CLI credentials. New live OAuth and private endpoint entitlement remain user/provider acceptance.

### Optional official Grok CLI renewal

Read-only `grok_cli` monitoring cannot keep an expiring bearer alive by itself. **Account setup → Enable automatic Grok renewal…** opens a separate owned **default-No** native review. After approval and successful identity/quota verification, `grok_cli_renewal` permits the installed official CLI's fixed `models` command **only after a real authentication rejection**, at most once per 15 minutes. The reviewed CLI build is **1.0.67 (2fe064390d07)**; unknown builds and custom authentication/deployment configuration fail closed. It can renew/replace its own saved credentials and may request authentication in its own browser; this is explicitly not read-only. OpenToken sends no refresh grant, model prompt or automatic extra `grok login` command.

The existing saved identity/profile must match before/after the owner operation, followed by ordinary authenticated identity/quota/source checks. An active interactive login excludes background renewal; both use one owner-operation lease. Version/models subprocess deadlines are 5/25 seconds, the whole observation is bounded to 60 seconds, stdout/stderr are bounded/zeroized and raw output never reaches WebView/logs. Ambient auth/config/debug overrides and self-update are disabled. Provider pauses still apply. Failed verification does not reuse this mode's old quota. Grants persist only in primary settings, not recovery backups; **Disconnect** or a successful **Use existing Grok** stops the permission. Owner-side credential changes already completed cannot be rolled back by cancelling or by a failed preference save. [Investigation and acceptance](GROK-SESSION-2026-10-23.md).

## Connect Codex or Claude

1. Select **Use existing Codex / Claude** first. Existing configured/default sources are verified and enabled without creating a managed profile, launching login or changing provider credentials. Local history remains separate from quota.
2. Only to add another account or explicitly authenticate: open **Account setup (only if needed)**, choose the official sign-in action, then finish its CLI/browser window. Codex uses `codex login`; Claude uses `claude auth login --claudeai`, not Console/API billing. OpenToken verifies available subscription usage and connects automatically, including after hiding the popup or navigating away.
3. Each added account receives a separate app-managed CLI home under `%LOCALAPPDATA%/OpenToken/sign-ins/{provider}/{opaque-id}`. No folder entry, browser-cookie extraction, password collection, OAuth impersonation or credential copying is involved. The CLI owns and writes its own credentials. Existing standard/custom configured/discovered homes keep working; there is no forced migration.
4. **Cancel sign-in** stops checking/waiting and terminates only the sign-in child launched for that run. The external browser is not closed and already-created provider credentials are not deleted or revoked. Verification already handed to the engine may finish. CLI waiting is bounded to ten minutes for ordinary MFA/SSO; cached status reads do not launch a CLI or poll credentials. Windows sign-in children get real console handles rather than inheriting GUI pipes/null handles, and nested/simple-mode credential overrides are stripped. A pending account is reused after cancellation/error/restart; a committed account is never overwritten by the next Add action.
5. **Accounts → Disconnect** stops monitoring all known sources for that identity, without logging it out or deleting credentials. Existing local history is retained under the usual retention policy. Account nicknames still work. The manual Login folder, Browse, Connect folder and Tracked folders sections have been removed from the UI; legacy path settings remain compatible in the backend.

Only installed native CLI executables are launched, without a shell, installer or downloaded code. A missing CLI gives an official installation link. Subscription/API-token and alternate-endpoint overrides are cleared for the child; no credentials or CLI output are collected by the sign-in coordinator. Private bounded local metadata markers and child exit status signal readiness; the actual engine adapter must verify usage before preferences/card/tray publication. A successful CLI exit alone is not a connected account. Verification uses existing provider gates (15-second spacing, 20 attempts/hour) and propagates rate-limit pauses. Persistence failure leaves provider credentials untouched and does not publish a successful connection. Stale generic preference saves preserve newly added managed homes, and targeted event merges preserve unrelated unsaved drafts and startup/pin choices.

This is not an importer for every other app profile. No new connector is claimed for unsupported providers. Claude's existing source-scoped identity handling remains; no authenticated email is fabricated when the usage endpoint does not supply one. Live newly launched Codex/Claude sign-in still requires user/provider acceptance; tests use synthetic sign-ins.

## Connect personal Cursor (default)

1. Select **Cursor → Use existing Cursor** to verify its current desktop session without opening login. If authentication is actually required, explicitly enter **Account setup (only if needed) → Sign in with Cursor**. The button tooltip and accessible description explain read-only desktop-session access and the unofficial usage source; there is no caption/info row underneath, separate consent checkbox or second Connect step.
2. If Cursor is already signed in, OpenToken verifies and connects it directly. Otherwise Cursor opens for normal sign-in and OpenToken waits in the background, then connects automatically. The native launcher checks standard user/Program Files installations without a shell, installer or arbitrary PATH executable. Custom installs can be opened manually; missing-app errors offer a Get Cursor link.
3. **Cancel sign-in** stops read-only checking/waiting. Once provider verification is committing, the transaction is allowed to finish rather than claiming a rollback. Waiting is bounded to two minutes; unchanged rejected tokens are not repeatedly submitted. A changed local session can be retried with the existing verification spacing/backoff.
4. The native coordinator continues across hiding/navigation, with pushed status and canonical connection metadata. It verifies account and usage before saving. **Accounts → Saved provider connections → Disconnect** stops monitoring without changing Cursor's sign-in/database, and clears stale sign-in status. Monitoring after a successful connection survives restart.

No Enterprise key, pasted browser cookie or API token is required. This mode reads only the `cursorAuth/accessToken` row of the standard `%APPDATA%/Cursor/User/globalStorage/state.vscdb` using bounded read-only SQLite access, off the UI thread. The app-owned data-directory override does not change the selected Cursor profile; automated native tests separately redirect the child's APPDATA to an empty fixture. No background credential lookup occurs without a persisted personal connection or an explicitly started sign-in request. Cached sign-in status reads do not inspect credentials; only an active native sign-in run probes the local row, at a bounded cadence. Private probe markers never enter events or logs. Portable/custom Cursor profiles and CLI-only sign-ins are not automatically searched or imported in this version.

Normal WAL reads include committed WAL state; idle databases with no sidecars use immutable read-only access so no WAL/SHM files are created. Unpaired sidecars, active rollback journals, reparse-linked sources, oversized values and unsupported encodings fail closed. No whole-database or browser-profile copy is made; existing SQLite shared-memory coordination is distinct from modifying credentials. UTF-8 and ASCII UTF-16LE sign-in values are supported. SQL value size, busy timeout and progress deadline are bounded.

The Rust adapter checks JWT structure/subject/expiry (with a 60-second margin), authenticates to fixed `https://cursor.com/api/auth/me`, reads `/api/usage-summary`, authenticates again, and rereads the local sign-in. A changed subject, email or token cannot publish a cross-account reading. JWT decoding is only a consistency check, not signature verification; the provider authenticates the session. Cursor owns and refreshes its tokens; OpenToken never renews, copies into its vault, overwrites or deletes them. Working tokens are zeroized where owned and never returned through IPC, settings, cache, logs or usage reports.

**The personal dashboard is unofficial/undocumented and can change.** Source labels in the panel, details, mini stripe and tray make this explicit. Only finite, actually reported total/Auto/API percentages and supplied billing-cycle dates become quota windows; missing/unlimited/team-only data does not become 100% left, a guessed limit or an individual pool. The personal badge/stripe uses the provider-reported **Monthly plan total**, not the most exhausted independent Auto/API bucket. Only when that total is absent does it fall back to the reported API bucket, then Auto; the tooltip names the selected reading. Auto/API cards stay separate and no total is averaged or fabricated. Enterprise still uses its separately scoped reported on-demand budget. Raw API percentages remain percent used. Monthly allowances are not relabelled as weekly/session quotas. Private usage is not inserted into local token counts, API-equivalent estimates or invoices.

Credential-file notifications are fingerprinted so ordinary database changes with the same readable token do not force quota reads. Authentication changes clear previous readings and schedule verification while preserving the read budget, short spacing guard and provider backoff. Transient unreadable watcher samples do not prove an account switch; scheduled reads retain the usual stale/error behavior. Minute reconciliation remains the fallback. Account changes require reconnecting the new account explicitly; a verified reconnect replaces the previous personal identity for that profile without overwriting Enterprise connections or unrelated preferences.

Implementation/protocol research is recorded in [CURSOR-RESEARCH.md](CURSOR-RESEARCH.md). This is an original Rust implementation, not a bundled upstream tracker or browser-cookie extraction library. Cursor's official CLI browser login remains a potential separate integration; this version launches/reuses the desktop app rather than depending on unverified CLI token-export behavior.

## Connect Cursor Enterprise (advanced)

1. Select **Cursor** in the grid, or choose Cursor under **Accounts → Connect existing usage**, then open the small **Enterprise setup** link. **Back to personal sign-in** closes it and clears unsaved key fields.
2. Open Cursor API key settings and use an Enterprise team admin key with `admin:*` scope. **This is a privileged key**, not a restricted read-only key. OpenToken only calls the documented read operations, but the key itself can have broader administrative powers. Do not use it if that trust/access is unsuitable.
3. Enter the **exact active team member email** to monitor. An organization/admin key does not identify its creator or justify assigning a team's total to the current user.
4. Enter the key and choose **Verify & connect**. Identity, scope and available usage are checked before saving anything.

Official endpoints: `GET https://api.cursor.com/teams/members` and read-only `POST https://api.cursor.com/teams/spend`, using Basic authentication with the key as username and an empty password. Spending search is not identity proof: rows must match the verified member ID and exact email. Member identity is checked again after reading. Pagination is bounded to ten pages of 100 rows, with a 2 MiB response bound and 45-second whole-operation timeout. A missing spending row is unavailable, not $0.

Only a positive `effectivePerUserLimitDollars` supplies an on-demand budget percentage. It is explicitly labelled **On-demand budget**, never the included plan's remaining percentage. `spendCents` and `overallSpendCents` preserve fractional cents and are displayed separately; included usage value is not an invoice. No reset date is guessed. A changed admin key creates a distinct scope, conservatively preventing cached usage from crossing teams even if the member ID/email is shared; disconnect the old entry after rotating keys.

Personal Cursor login and Cloud Agent API keys are **not substitutes** for Enterprise Admin API access. Personal desktop monitoring is a separate, explicitly consented mode described above. The Enterprise adapter itself does not use browser sessions, private dashboard endpoints or Cursor credential databases.

## Connect Copilot (default)

Choose **Use existing Copilot**. OpenToken reads the installed official GitHub CLI's current `github.com` login and verifies identity/usage without opening OAuth. If necessary, explicitly enter **Account setup (only if needed) → Sign in with GitHub** for the separate provider-owned CLI/browser flow. ## Connect Z.ai, DeepSeek, Kimi Code or OpenCode Go

Select the provider, choose the applicable region (Z.ai/Kimi), open its key settings, enter the eligible API key **inside the app**, then **Verify & connect**. Successful usage is required before storing the key in Windows Credential Manager or publishing a card. Public metadata identifies a key scope, not an invented human/email; region and a hashed key scope prevent cross-key/region caching. Region changes discard unsaved keys. Disconnect removes only the app-owned key and monitoring metadata, not provider-side keys/accounts. Rotation is a new scope; remove the old entry explicitly.

Destinations are fixed HTTPS hosts, redirects disabled and JSON bounded; there are no endpoint overrides from UI/settings/env. Z.ai uses `api.z.ai`/`open.bigmodel.cn` `/api/monitor/usage/quota/limit`; Kimi uses `api.kimi.com`/`api.kimi.ai` `/coding/v1/usages`; DeepSeek uses `api.deepseek.com/user/balance`; OpenCode Go uses `opencode.ai/zen/go/v1/usage`. Quota endpoint stability is not promised. Missing fields remain unavailable, not zero. DeepSeek balances stay per currency with no percentage. These APIs do not enter CLI token history/value estimates or invoice totals. See [the full provider audit](PROVIDER-RESEARCH.md) for evidence and protocol limitations, and [the new native source modes](REMAINING-PROVIDERS.md) for Antigravity/Devin/Muse. Grok/Kimi/Muse local recorded usage is separate and does not require these quota credentials.

## Connect personal GitHub Copilot billing (advanced)

1. Select **Copilot**, or choose it in Accounts, then **Advanced personal billing**. The compact form keeps its longer scope/storage explanations in optional disclosures; it does not pretend that a normal GitHub browser login provides billing access.
2. Open GitHub token settings. Create a **fine-grained** personal token for the account that pays for its own Copilot plan, with only **Plan: read** under user permissions. No repository permissions are required.
3. Choose a sensible token expiry, paste it into the password field and select **Verify & connect**.

Official requests use fixed `https://api.github.com` URLs, `Accept: application/vnd.github+json`, API version `2026-03-10` and Bearer authentication:

- `GET /user`: bind to the authenticated numeric user ID, never an email guess.
- `GET /users/{verified-login}/settings/billing/premium_request/usage?year=…&month=…`.
- `GET /users/{verified-login}/settings/billing/ai_credit/usage?year=…&month=…`.
- `GET /user` again: reject an identity change around the read.

Reports must match the verified login and requested period. Only Copilot products and the endpoint's expected request/credit units are included. Request quantities and AI-credit quantities are **not added together**. Their reported net usage amounts are separate values, not a synthesized invoice or the local API-equivalent spending donut. These endpoints do not provide a verified allowance denominator: the panel/tray do not invent percent-left. An empty personal report does not establish zero usage or that a plan exists. HTTP 404 for one unavailable report can leave the other usable; neither report accessible is an access error. Permission failures clear cached readings, while transient network errors disclose same-identity stale values.

GitHub documents that user billing endpoints exclude organization/enterprise-paid Copilot usage. Classic OAuth/CLI tokens are not advertised as substitutes for the required fine-grained user permission. There is no embedded password page or borrowed OAuth app/client ID; browser-based OAuth can be added only with an appropriate registered application and supported billing scopes.

## Storage, updates and disconnect

- Submitted keys stay out of settings, cache, diagnostics, clipboard reports and HTTP API responses. The password field clears on submission. They are sent only through local native IPC to Rust and then to fixed official HTTPS destinations; redirects are disabled. Submitted Rust tokens and working read tokens use zeroizing wrappers where owned; this is not a guarantee that OS, WebView, HTTP or allocator memory contains no transient copies.
- App-owned secrets are saved in **Windows Credential Manager**, under an OpenToken-only target namespace bound to the data directory and connection ID. No other application's entries are enumerated, copied, renewed, modified or deleted. Moving a custom data directory changes the namespace and requires reconnecting.
- Settings schema 1 has a default-empty `connections` list containing only public identity/scope metadata. New `mode` defaults to `api` for existing entries; `cursor_app` records consented monitoring and its profile path, never a copied token. Old profiles keep working. Targeted engine commands serialize connect/disconnect with settings writes; a failed settings write attempts to restore the previous secure credential. Rollback failures are disclosed. General preference saves cannot add, overwrite or erase secure connections.
- Ordinary reads use the existing background scheduler, concurrency bound, stale/identity handling and per-account read-cycle budget. Connection verification has a 15-second/provider burst guard and at most 20 attempts/provider/hour/run; provider Retry-After/rate-limit pauses also block reconnect attempts and other connections. Budgets/backoff are in-memory and reset with the process. Copilot billing and Cursor reports may lag actual activity; this is not per-request live metering.
- **Accounts → Saved provider connections → Disconnect** removes OpenToken's saved API credential and active card/tray entry. Provider-owned session modes (Cursor/GitHub/Grok/Devin/Antigravity/Muse) only remove monitoring metadata and never delete the client's credentials, terminate its app or touch the app-owned vault. Muse key-endpoint approval is not retained in automatic settings backups, to avoid resurrecting it after disconnect/recovery. It does not sign you out of Cursor, GitHub, Codex or Claude or revoke the key at the provider. Revoke keys separately in the provider dashboard when appropriate. Removing the last API connection does not silently enable a CLI connector. Cache/backup metadata is not secure erasure.
- Existing local Codex/Claude tracking and credential ownership remain unchanged. API usage values are not inserted into local token history, estimated spending or observed CLI-credit changes.
